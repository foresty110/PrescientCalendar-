# 종일 일정은 스키마 플래그 없이 duration 휴리스틱으로 분리

- 결정일: 2026-05-15
- 상태: accepted
- 맥락: 타임라인 Phase 3 (FEATURES `5.3-b` 종일 일정 분리 영역)

## 맥락

오늘의 일정 타임라인에 "종일" 분리 영역이 필요. 현재 `Event` 모델은
`scheduledStartAt` + `scheduledDurationMin` 만 갖고 있고 종일 여부 플래그는
없다. 어떻게 종일을 판정·표시할지 결정해야 함.

## 선택지

1. **`Event.isAllDay Boolean` 스키마 필드 추가**
   - 명시적, 정확.
   - 단점: 마이그레이션 + `create_event` / `update_event` Zod 입력
     스키마 변경 + LLM 시스템 프롬프트에 "종일 의도 추론" 룰 추가까지
     연쇄 작업. 사용자가 "워크샵 종일" 이라 말했을 때 LLM 이 플래그를
     세팅하는 룰을 새로 학습시켜야 함.

2. **duration 기반 휴리스틱** (`scheduledDurationMin >= 22 * 60`)
   - UI 레이어 1줄짜리 헬퍼.
   - 단점: 24h 짜리로 "장기 행사" 를 등록한 경우와 진짜 종일을 구분
     못 함. 다중일 일정도 24h 단위로 등록되면 종일로 분류됨.

## 결정

**선택지 2 (휴리스틱)** 채택. `src/components/timeline/status.ts` 에
`ALL_DAY_THRESHOLD_MIN = 22 * 60` 상수 + `isAllDayDuration(min)` 헬퍼.
판정은 UI 레이어에만 존재. DB / LLM / API 계약은 무변화.

## 근거

- 5.3-b 는 "분리 영역(UI 표현)" 이 본질이다. 데이터 모델의 진실 (이게 정말
  종일 의도인가) 과 UI 의 진실 (이건 종일처럼 보여야 하는가) 을 동시에
  풀 필요가 없다.
- 22h 라는 큰 threshold 면 9-to-5 워크샵(8h) 같은 긴-시간형 일정은 자연히
  시간형으로 남는다 — false positive 위험이 낮다.
- 사용자가 "22h+ 인데 시간형으로 보고 싶다" 는 피드백을 주면 그때
  스키마 필드를 도입한다 (YAGNI).

## 트레이드오프 / 알려진 한계

- 24h 이상으로 만든 "장기 출장" 같은 다중일 일정도 종일로 표시된다.
  현 도메인에 다중일 일정 모델 자체가 명확히 정의돼 있지 않으므로
  큰 문제는 아니다 — 다중일 일정을 정식으로 모델링할 때 함께 재설계한다.
- `update_event` 로 duration 을 21h ↔ 23h 사이로 옮기면 시간형 ↔ 종일
  표시가 토글된다. 의도된 동작 (UI 가 데이터를 그대로 반영).

## 후속

이 결정은 5.3-b 의 UI 분리 영역 구현으로 끝난다. 별도 후속 작업 없음.
