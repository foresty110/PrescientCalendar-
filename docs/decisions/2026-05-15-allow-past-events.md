# 과거 시각 일정 생성 허용 + 저장 전 사용자 재확인

- 결정일: 2026-05-15
- 상태: accepted
- 맥락: 사후 기록 시나리오 (회고가 아니라 과거 시각 자체를 일정으로 기록)

## 맥락

기존 `createEvent` 는 `startAt` 이 `now` 보다 과거면 `PAST_TIME` 에러로 거부했다. 시스템 프롬프트(`scheduler.md §3`)도 "과거 시각은 회고로 처리하라고 안내" 룰로 막았다.

문제: 사용자가 "지난주 화요일 9시 회의 추가해줘" 처럼 **사후로 일정 자체를 기록**하고 싶은 경우(예: 캘린더에 빠진 일정을 채워 넣기, 출장/연차 같은 사실 기록) 를 처리할 수 없었다. 회고(`record_actual_run`) 는 *기존* ScheduledRun 에 대한 실행 결과 기록이라 목적이 다르다.

## 선택지

1. **그대로 거부, 회고 시스템으로 안내** — 현재 동작. 사용자 입장에서 "추가해줘" 의도가 막힘.
2. **무조건 허용, 확인 없음** — 빠르지만 오타 입력 시 의도치 않은 과거 일정이 쉽게 생성.
3. **허용 + 저장 전 사용자 확인** — 도구 호출 직전에 "지나간 시각인데 추가할까요?" 한 마디 확인.

## 결정

**선택지 3**: `createEvent` 의 `PAST_TIME` 가드를 제거해 과거 시각 모두 허용. 동시에 `scheduler.md §3` 룰을 "과거 시각이면 호출 전에 사용자에게 한 번 더 확인 + 회고 어조와 구분" 으로 재작성. 도구 설명(`tools.ts` createEventTool description) 과 `docs/llm-tools.md` 도 일치시켜 일관.

`recurrence` 도 과거 anchor 허용 — `expandRecurrence` 가 anchor 부터 horizon(4주) 안의 instances 를 만든다. "지난 월요일부터 매일 책" 같은 입력이 자연스럽게 동작 (사용자 명시 동의).

## 근거

- 사용자 직접 요청: "이미 지난 요일·시각의 일정을 생성할 수 있는 기능". 무제한 과거 허용 명시.
- 회고와 명확히 분리: 회고 어조("했어/늦게 시작했어") → `record_actual_run`. 명시 요청("추가/잡아줘") → `create_event`. 모호하면 LLM 이 되묻는다.
- 오타 방지: 저장 전 확인 메시지 한 단계로 의도치 않은 과거 일정 생성을 막는다 — UX 비용 작고 안전성 큼.
- 충돌 처리는 그대로 적용: 과거에도 같은 시간대에 다른 일정이 있으면 거부 + 대안 제시. 도메인 불변식 "캘린더에 시간 충돌 없음" 유지.

## 트레이드오프

- 사용자가 "어제 9시에 회의 있었어" 만 한 줄 보내면 LLM 이 "회고 vs 생성" 두 가지 사이에서 판단해야 함. 가이드라인 따라 모호하면 되묻기. 첫 응답 한 턴이 추가될 수 있음 (UX 비용).
- feasibility 점수가 과거 일정에도 자동 산출되지만 의미가 약함 (이미 끝난 일정의 실현 가능성). 캘린더는 chip 색상으로 회고 필요 여부만 표시하므로 점수 영향 미미.
- API 라우트에서 `mapError` 의 `PAST_TIME` 분기를 제거 — dead code 정리. 추후 다른 곳에서 `PAST_TIME:` prefix 에러를 던질 일이 없도록 코드 베이스 일관 유지.

## 후속

- `update_event` 도 비슷한 분기를 가질 수 있는데, 현재는 startAt 변경을 직접 지원 안 하고 `delete + create` 조합이므로 영향 없음.
- 회고/생성 의도 판단이 잦은 오해를 일으키면 분기 룰을 더 단단히 (예: 사용자 입력에 동사 패턴 매칭) 검토.
