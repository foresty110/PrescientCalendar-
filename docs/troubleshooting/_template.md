- 날짜: YYYY-MM-DD
- 영향 범위: <어디서 터졌나 — 빌드/CI/로컬/prod 등>
- 관련 기능: FEATURES.md X.Y

> **작성 원칙 — 처음 보는 사람도 읽고 이해할 수 있게.** "내가 뭘 했나" 가 아니라 "이 시스템에서 무슨 일이 있었나 → 왜 그게 어려운 문제였나 → 어떻게 풀었나" 흐름. 약어·고유명사(예: P1012, IDOR, alias URL, JWE, silent skip…) 는 처음 등장할 때 한 줄로 풀어 적거나 괄호 부연. 6개월 뒤 자신·신규 동료·면접관 중 한 명이 읽고도 흐름이 잡혀야 한다. 자세한 가이드는 `README.md` "작성법" 참고.

## 무슨 일이 있었나

먼저 배경부터: 이 시스템에서 평소엔 어떻게 동작하는 게 정상이고, 이번엔 그게 어떻게 어긋났는지를 처음 보는 사람에게 설명하듯. 도메인 용어(예: "Vercel 의 preview 배포가 뭔지", "Auth.js 의 DB session 이 뭔지")가 등장하면 한 줄로 풀어 적는다.

그 다음 실제 본 증상 — 에러 메시지, 화면 상태, 빌드 로그 등을 인용 박스로:

> 실제 에러/현상 그대로 (붙여넣기)

## 왜 풀기 까다로웠나 (선택)

표면 증상과 실제 원인이 다른 경우, 혹은 어디서부터 의심해야 할지 단서가 부족했던 경우만 별도 섹션으로. 단순한 케이스면 생략하고 "시도한 가설" 로 바로 진행.

## 시도한 가설

각 가설은 **결과** 까지 표기 — 확정인지 거짓인지, 거짓이라면 무엇이 그렇게 판단하게 했는지.

- **H1**: ... → 확정/거짓 (근거)
- **H2**: ... → 확정/거짓 (근거)

## 원인

가설 단계에서 확정된 근본 원인. **무엇이 어떤 조건에서 그렇게 동작하는지** 까지. "X 가 누락" 정도가 아니라 "X 가 어떤 시점에 어떤 의존 관계로 필요한데 어디서 빠졌는지".

## 해결

무엇을 어떻게 바꿔서 고쳤는지. 코드 변경이면 커밋 SHA 또는 PR 링크, 외부 설정이면 어디서 무엇을 바꿨는지 구체 경로.

대안을 비교했다면 표로:

| 옵션 | 결정 | 이유 |
|---|---|---|
| A | 기각 | ... |
| B | 채택 | ... |

## 재발 방지

- 가드레일/테스트/문서/도구 어디에 어떻게 반영해야 같은 함정에 다시 안 빠지는지
- 후속으로 미룬 항목이 있으면 별도 PR/이슈 링크 또는 "별도 PR" 명기
